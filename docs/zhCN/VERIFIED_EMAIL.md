# 可信邮箱验证声明

Stargate 的 `CheckRoute` ForwardAuth 端点仅在以下条件全部满足时返回
`X-Auth-Email-Verified: true`：Warden 会话经过 Herald 的**邮箱通道**验证，
服务端保存的 challenge ID、显式 Warden 用户 ID 和当前目录邮箱全部匹配。
认证成功但缺少这些证据时返回 `false`；认证失败不输出此声明。

声明证明当前邮箱控制权，不证明历史邮件归属，也不保证用户 ID 永不重新分配。
OwlMail 等应用仍需稳定且不可复用的身份和独立的历史认领策略。Warden 可要求
显式用户 ID，但其生命周期仍由管理员负责。

## 证据与有效期

成功验证后，在服务端会话保存主体、规范化邮箱、验证时间、证据来源
`herald-email-challenge` 和格式版本。域名进行 IDNA 转换并转小写；ASCII
邮箱 local part 保持精确，包括大小写和加号。不支持的地址格式不获得声明，
也不从 AMR 推导验证事实。

证据在现有 `SessionExpiration` 的 24 小时后过期，不因会话访问或权限刷新延长。
每次输出都核对认证结果的主体和当前邮箱。目录刷新发现邮箱变更或移除时永久删除
旧证据，之后改回也不会恢复。退出登录销毁会话，新登录重置旧身份状态。
旧会话仍可正常使用，但没有证据时返回 `false`。

短信、TOTP、共享密码、密码头、可信身份请求头、目录列出的邮箱以及泛化的
`otp`/`email` AMR 都不能生成该证据。challenge 上下文缺失或不可用不破坏
原有合法登录路径，但不能输出 `true`。

用户吊销仍受现有权限刷新配置和实际查询/缓存窗口约束，并不因此变成立即生效。
受保护部署需要启用并实测相应刷新策略和失败拒绝行为。

## 反向代理集成

只从可信 Stargate 认证成功的响应复制此头，并同时复制 `X-Auth-User` 和
`X-Auth-Email`。将 `X-Auth-Email-Verified` 加入代理明确的认证响应头白名单。
转发应用请求前剥除客户端自带的身份头，限制应用后端直连；禁止在代理配置中固定
设置验证为 true。Stargate 也会删除发给自身认证端点的外部验证请求头。

OwlMail 多人公开发布门禁和真实身份/通知验收仍须保留，直到实际部署验证通过。
本实现的组件测试不能证明历史归属，也不能替代真实
Stargate/Warden/Herald/Phorge 通知链路验收。
