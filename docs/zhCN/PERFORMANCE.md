# Redis 限流性能测量

## 范围与安全边界

本文记录 v1.2.6 之后的 Redis 固定窗口限流优化。原生客户端直接解码脚本返回的
两个整数，减少通用回复、整数装箱及整数切片转换。该路径用于原生 `Client`、
`ClusterClient` 和 `Ring`。自定义适配器仍使用 `Script.Run`，保留其覆盖的
`Eval`/`EvalSha` 方法及延迟执行客户端语义。原生 process hook 现在收到的脚本命令
是 `*redis.IntSliceCmd`，此前为 `*redis.Cmd`；自定义 hook 应使用 `redis.Cmder`
接口或兼容该类型。若 hook 断言旧的具体类型，部署前需先更新。HTTP 字段、
配置名、指标名称和标签均不变。

Lua 文本及 SHA-1（`77b796d33596742046596a01e3b879c9d1b19715`）不变，计数器创建和
过期时间仍原子提交。毫秒窗口、旧的无过期计数器、Redis 键名、ACL 命令和已有
记录均兼容。两种脚本命令均指定首个键的位置，保持集群路由。仅 `NOSCRIPT`
允许应用层改用 `EVAL`，因为它明确表示脚本尚未执行；其他错误继续返回。原有
本地降级计数及底层 Redis 客户端重试策略不变，不会删除计数器、换键、放宽
配额或忽略写入错误。

回复必须能够解析为恰好两个整数。在 miniredis 提交计数后注入空回复，v1.2.6 会出现
越界 panic；回归测试中，新实现返回错误、保留已提交计数，并继续执行有界的
本地降级计数。这是畸形回复可靠性测试，不是认证绕过漏洞报告。

## 2026-11-02 本地排查

环境与上轮一致：Linux arm64，内核 `7.0.9-205.fc44.aarch64`，Go 1.27.3，
Redis 8.2.1，5 个 vCPU，报告内存 5,609,476 KiB。冷路径创建新计数器键，热路径复用已有有效键；脚本
在计时前加载。这是存储层操作基准，不是完整认证请求基准。计时前先编译两个二进制，
使用相同基准、依赖、Redis 和回环 TCP 配置。历史对照仅把 `ratelimit.go`
替换为 `a55659a` 中的原子化之前实现，其余条件不变。旧实现仅用于诊断，不能
为了速度回滚生产环境。

每个冷/热路径各执行 5,000 次操作，进行 12 轮 AB/BA 交替测量。本轮确认存在
热路径成本，但不是固定的 16%：历史/当前实现的热路径耗时中位数分别为
83,181/91,587.5 ns/op，配对耗时比中位数为 1.085，当前实现在 9/12 轮较慢。
冷路径中位数分别为 170,773.5/94,940 ns/op。热路径串行吞吐约为
12,022/10,919 次/秒。

独立诊断比较了历史 `TTL` 管线、`PTTL` 管线、当前脚本、未经整数切片转换的
脚本回复和 `PING`。Redis `INFO commandstats` 显示，`EVALSHA` 的服务端执行
时间约为 13–14 微秒，而 `INCR` 加 `TTL`/`PTTL` 合计约为 3–4 微秒。这是
包含调度影响的执行时间，不是操作系统 CPU profile；Lua 总时间已经包含内部
命令，不能再重复相加。`PING` 本身也在约 88 微秒附近波动，说明传输及调度
开销不可忽略。原子脚本增加了服务端成本，恢复旧管线会重新引入过期时间和
不确定写入状态问题。

早期原型比较期间，5 vCPU 的 VM 负载均值达到约 15 并继续升高，存在其他编译
和软件包任务。保留这批延迟样本，但不能据此断言提速或回退。所有样本中，
原型热路径分配稳定从 16 次降到 12 次，约 487 B/op 降到 400 B/op；冷路径
从 17 次降到 13 次，约 518 B/op 降到 438 B/op。分配减少不等于端到端延迟
已经降低。

## VM 恢复空闲后的最终实现

VM 恢复约 94% 空闲、1 分钟负载均值 0.09 后，又进行了完整 12 轮比较，基线为
`7f7c0b1`，候选为 `0d9e2b1`，两侧均包含 #225 后的依赖图。候选即本 PR 的
运行时代码，后续文档提交没有改变 Go 代码。先编译两个二进制，保留全部
48 个冷/热路径样本。

热路径分配从 16 次降到 10 次（减少 37.5%），487 B/op 降到 368 B/op
（减少 24.4%）。耗时中位数为 94,740.5/89,073.5 ns/op，串行吞吐约为
10,555/11,227 次/秒。配对耗时比中位数 0.963，描述性 95% bootstrap 区间
0.917–1.027，仍不能证明稳定的延迟改善；候选在 5/12 轮较慢。

冷路径分配从 17 次降到 11 次，517 B/op 降到 405 B/op；耗时中位数为
92,483/92,419 ns/op，串行吞吐约为 10,813/10,820 次/秒。配对耗时比 1.001，
区间 0.942–1.032，6/12 轮较慢，延迟在噪声范围内基本持平。分配改善可重复，
但没有证明历史热路径延迟差距已经消除。独立 PR runner 将提供另一组测量，
不会替换或丢弃这些样本。

## 可重复的 Linux 比较

使用独立测试 Redis 8.2.1 和 Linux Go 1.27.3，不得指向生产 Redis。计时阶段
不要并行编译、运行其他测试或采集 profile。脚本先编译两个版本，再使用同一
Redis 交替测量，并记录 VM 负载，保留全部样本。

```bash
STARGATE_TEST_REDIS_ADDR=127.0.0.1:6379 \
  python3 .github/scripts/benchmark-redis.py \
  --baseline 7f7c0b101baa1b58da98eda98c9a5c8a054100b0 \
  --output /tmp/stargate-redis-performance --rounds 12 --operations 5000
```

JSON 包含源码版本、工作区修改状态、环境、耗时、串行吞吐、字节数、分配次数、
负载均值及命令统计。服务端统计覆盖一次二进制调用中的冷/热路径、初始化和
基准校准。配对 bootstrap 区间仅为描述性统计，不能消除共享 VM 干扰。分配
profile 在计时结束后单独采集。PR CI 在独立 Linux arm64 runner 上重复比较，
上传原始日志、profile 和 JSON，保留 30 天；仅在限流代码、基准脚本或 PR
工作流变化时执行。基准报错或跳过会导致任务失败，不能因延迟噪声削弱功能
测试或 95% 覆盖率要求。

同一二进制内也可比较两种解码路径：

```bash
STARGATE_TEST_REDIS_ADDR=127.0.0.1:6379 \
  go test ./src/internal/handlers -run '^$' \
  -bench '^BenchmarkRedisRateLimitReplyDecoder$' -benchmem -count=12
```

## 兼容性与验证限制

本次优化无需迁移数据、新增持久卷、升级 Redis 或暂停流量。v1.2.6 与优化版本
使用相同脚本和记录，可以混合运行；回滚 v1.2.6 只恢复通用解码，不改变存储
数据。更早的已发布版本缺少 v1.2.6 安全及可靠性修复，不应作为回滚目标。

回归覆盖正常计数、最后毫秒过期、旧无过期计数器、脚本缓存清空、原始及标准化
`NOSCRIPT`、原生与适配器混用、RESP2/RESP3、ACL 拒绝、并发请求，以及写入已
提交但确认丢失。确认丢失在实际 Redis 写入后注入，并禁用客户端重试以检查
应用层行为，不是生产网络故障实验。集群路由使用两个 miniredis 目标验证，
不声称已验证生产集群故障转移。生产负载、Redis 持久化丢失、复制故障转移及
真实网络丢包仍需单独运维验证。
